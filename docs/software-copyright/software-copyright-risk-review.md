# 软著材料风险审查

## 1. 审查结论

当前软著材料可以作为老师初审版本使用。材料已将软件定位为机器人隧道巡检病害分析工程原型，明确主验证数据仍是 KICT 静态图像 / mask 与仿真巡检元数据；新增的真实巡检输入适配仅为单 sequence、已有 mask 的离线数据合同与就绪性校验。材料纳入路线级时空分析、比较证据与声明门控、固定任务契约和受控工作流，但未将当前结果描述为真实线路长期演化结论、在线平台或生产调度服务。

## 2. 数据来源风险

### 风险点

若材料把 KICT 静态图像 / mask 与仿真巡检元数据描述为真实现场连续巡检数据，会造成软件能力边界不清。

### 当前处理

登记草案、功能说明书和用户手册均明确写明：当前版本基于 KICT 静态图像 / mask 与仿真巡检元数据进行工程原型验证。

### 建议

后续对外提交或给老师审阅时，继续保留“静态公开图像 / mask + 仿真巡检元数据”的说明，不要删除边界声明。

## 3. 规则面积变化提示风险

### 风险点

规则面积变化提示容易被误解为真实病害发展预测或结构安全判定。

### 当前处理

文档中统一使用“规则面积变化提示”“复检辅助提示”等表述，并说明该结果不是结构安全结论。

### 建议

答辩或软著说明中应继续强调：该模块用于辅助整理和复检提示，正式工程结论需要人工复核和专业检测流程确认。

## 4. Web Dashboard 表述风险

### 风险点

Web Dashboard 容易被误写成已经完成真实数据上传、任务调度和工程上线流程的系统。

### 当前处理

文档中将 Web Dashboard 定位为本地展示界面，用于展示已经生成的 demo 分析结果。真实数据上传、异步任务和结果管理被写为后续扩展方向。

### 建议

如后续申请材料中需要截图，可配合说明“本地演示界面”和“结果展示界面”，避免写成已完整上线运行的平台。

## 5. 模型能力表述风险

### 风险点

如果把当前模型或单图检测能力写成已满足现场验收要求，会造成能力夸大。

### 当前处理

文档只说明单图检测用于辅助复核和结果对照；若没有人工 GT 标注，一致性指标不能作为真实分割精度。

### 建议

软著材料重点写软件功能和流程，不把模型精度作为核心权利点，也不使用未经正式验证的现场效果描述。

## 6. 视频 demo 与实时分析表述风险

### 风险点

新增视频 demo、OpenCV 标注视频和 Supervision 标注视频后，材料容易被误写成“已支持真实机器人视频上传、实时视频流分析或自动模型推理”。

### 当前处理

文档中将 `tunnel_demo.mp4` 明确描述为由 KICT 静态图像 / mask 合成的 demo video，用于验证视频输入处理、标注帧生成、标注视频导出和 Web 展示流程。Supervision 被描述为可选可视化工具层，不参与 Disease Memory Bank、no-id Association 和规则面积变化提示等核心逻辑。

### 建议

正式说明书或答辩材料中可以展示视频分析结果页面和标注视频，但应配合说明“本地演示视频”“已有 mask 输入”“可选可视化层”，不要写成真实视频上传平台、实时视频流系统或现场自动检测系统。

## 7. 路线级趋势与声明表述风险

### 风险点

连续帧聚合、面积变化或 defect track 容易被误写为已经证明病害真实增长，尤其是同一轮巡检内的重复观测。

### 当前处理

路线级输出保留 `comparability_status`、`claim_level` 和 `measurement_basis`。同一轮次变化仅表述为 `apparent-change-evidence`；只有可比较的跨轮证据或人工确认才允许表述为 `suspected-growth`。

### 建议

说明书截图、图注和答辩讲解应同时展示或说明上述三个字段。不得把 `suspected-growth` 写成已确认增长，更不得把任一趋势字段写成结构安全结论。

## 8. 真实巡检输入适配风险

### 风险点

单 sequence 的已有 mask 输入适配，容易被误写为已完成真实机器人数据接入、在线推理、跨轮关联准确率评测或长期趋势验证。

### 当前处理

材料明确该模块只验证图像、已有 mask 和严格工程元数据的数据合同、完整性清单及就绪性；不包含在线上传、自动模型推理、真实跨轮 Ground Truth 评分或增长结论。

### 建议

对外材料采用“真实巡检输入适配基础层”或“离线输入准备”表述，避免使用“已完成真实现场闭环”“已验证真实增长”等表述。

## 9. 受控工作流与上线表述风险

### 风险点

状态快照、运行锁、操作日志、恢复与发布机制容易被误写成已经上线的任务调度、多人协同或云端服务。

### 当前处理

该能力仅在隔离临时沙箱内按固定任务契约运行；Web Dashboard 只展示结果，不触发该工作流。

### 建议

软著材料可描述“离线受控任务执行、状态记录、异常阻断与受控维护处理”，不要描述为在线任务队列、生产调度平台或多租户服务。

## 10. 论文创新点与软著功能混淆风险

### 风险点

论文材料强调算法创新和实验论证，软著材料强调软件功能、模块结构和用户操作。两者混写会导致软著材料不够清晰。

### 当前处理

本次材料以软件模块、数据流程、操作方式和输出产物为主，避免写成论文式实验结论。

### 建议

软著申请材料中优先保留“模块、流程、输入输出、操作说明”，论文或专利中的实验指标可作为附加背景，不建议作为软著主线。

## 11. 路径与个人信息风险

### 风险点

仓库中存在本地绝对路径、实验目录、环境路径和生成产物路径。直接提交可能暴露个人电脑路径或造成材料不规范。

### 当前处理

源代码提交建议中已要求避免个人绝对路径、数据集、模型权重、缓存和日志。

### 建议

正式提交源代码页前，应统一检查：

- 是否存在 `C:/Users/...` 这类个人路径；
- 是否包含账号、令牌、私有地址；
- 是否包含大模型权重或数据集；
- 是否包含缓存、日志、临时文件。
- 是否误提交 `data/videos/`、`data/video_frames/`、`data/video_inspection/`、`data/video_masks/`、`outputs/video_inspection/` 等本地生成视频 demo 产物。

## 12. 申请规范格式风险

### 风险点

用户说明书和源代码材料如果不符合学校模板要求，可能在形式审查阶段被退回。例如封面或页眉误写版本号、源代码材料缺少“源程序前30页 / 源程序后30页”标记、用户说明书没有图片等。

### 当前处理

材料清单、用户手册草案和源代码提交建议已补充以下要求：

- 用户说明书封面使用“软件名称 + 用户使用说明书”，封面和页眉不写版本号；
- 用户说明书正式版至少包含一张界面图或流程图；
- 源代码封面使用“软件名称 + 源代码”，源代码材料不需要目录；
- 超过 60 页时按“源程序前30页 / 源程序后30页”整理；
- 页眉只写软件名称，页码放在页面右上端。

### 建议

正式提交前，应按学校提供的 Word 模板重新排版，并由申请人逐页检查封面、页眉、页码、图片编号和源代码页标题。

## 13. 学校流程与权属风险

### 风险点

若项目按学校流程申请，著作权人、第一开发者、授权码、签章页和学校知识产权系统登记流程需要与学校要求一致。当前材料按“著作权人：西安理工大学；第一开发者：陈志鹏；发表状态：未发表；权利取得方式：原始取得”的口径整理。若以 2026 年 7 月 30 日功能基线申报，开发完成日期建议按该日期与内部完成记录核验；学校端办理路径、授权码和签章页仍需按学校要求确认。

### 当前处理

登记草案和材料清单已将“西安理工大学”“陈志鹏”“我是代理人”“授权码”“学校知识产权系统”等内容写为当前建议口径及学校规范办理注意事项，并提示最终由指导老师或学校知识产权管理部门确认流程细节。

### 建议

正式提交前，已确认的申报口径为：

- 著作权人填写西安理工大学；
- 第一开发者填写陈志鹏；
- 开发完成日期按最终锁定的申报版本与内部完成记录填写；若采用本材料基线，建议核验 2026 年 7 月 30 日；
- 发表状态填写未发表；
- 权利取得方式填写原始取得，或按申请系统选项填写原创取得。

仍需按学校流程确认：

- 学校知识产权系统中选择教师软件著作权申请还是学生软件著作权申请；
- 签章页打印、盖章、上传和授权证书成果登记是否按学校流程完成。

## 14. 人工补充信息清单

正式申报前仍需要人工补充或确认以下信息：

1. 申请人身份信息和学校系统账号信息；
2. 是否存在共同开发者或其他署名要求；
3. 学校端申请入口、授权码、签章页和盖章流程；
4. 最终提交的软件名称和简称是否与申请表、说明书、源代码封面一致；
5. 源代码页数、说明书页数和正式截图；
6. 是否需要对本地路径、个人路径或测试数据路径做脱敏处理。

## 12. 结论

当前材料适合作为软著申请前的初审稿。正式提交前，应由陈志鹏和指导老师确认学校流程、授权码、签章页、源代码节选范围、正式说明书截图，以及是否需要加入 Web 视频分析结果界面或标注视频截图作为说明书插图。
